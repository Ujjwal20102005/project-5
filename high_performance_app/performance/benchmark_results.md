# Benchmark Results

Environment: Python 3.12.3, 1 CPU cores, Linux-6.18.44-fc-v165-x86_64-with-glibc2.39
Generated by `scripts/benchmark.py` (numbers vary by machine; relative gains are what matter).

| Optimization | Before | After | Improvement |
|---|---|---|---|
| asyncio concurrency (300 I/O calls @ 20 ms) | 6.134 s (48.9 rps) | 0.067 s (4490.2 rps) | **91.8x** |
| Process pool vs thread pool (96 CPU-bound records, 1 cores) | 1.266 s | 1.301 s | **0.97x** |
| LRU/TTL cache (cold vs warm, hit rate 50% overall) | 3.099 s | 0.006 s | **490.9x** |
| Batched DB writes (3000 rows) | 0.16 s | 0.0077 s | **20.8x** |
| Composite index on hot query (300,000 rows) | 18.436 ms | 0.055 ms | **334.3x** |


> **Note:** this run had a single CPU core, so the process-pool row cannot show a gain (processes only help when >1 core is available). Re-run on a multi-core machine; expect close to N-core scaling for CPU-bound work.

## Query plans
- Without index: `SCAN results; USE TEMP B-TREE FOR ORDER BY`
- With index: `SEARCH results USING INDEX idx_results_status_created (status=?)`

## End-to-end peak (fast strategy, 20,000 records, 32 workers, batch 500)
- Throughput: **55,610 records/s** (0.36 s total)
- Per-record processing latency (excludes queue wait): p50 0.009 ms, p95 0.017 ms, p99 0.05 ms
